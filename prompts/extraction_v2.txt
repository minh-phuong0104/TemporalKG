You are an expert information-extraction system for scientific knowledge graph construction.

Extract factual knowledge quadruples from the abstract below.
Each quadruple must link two SCIENTIFIC CONCEPTS with one technical relation and the publication year.

Return ONLY valid JSON. No markdown, no explanation, no comments.

Format:
[
  {{"subject": "", "relation": "", "object": "", "year": 2018}}
]

Allowed relation vocabulary:
- introduces
- proposes
- improves_upon
- outperforms
- is_based_on
- extends
- is_a_variant_of
- uses
- is_evaluated_on
- is_pretrained_on
- achieves
- addresses
- detects
- classifies
- predicts
- extracts
- generates
- reduces
- increases
- applies_to
- supports
- integrates
- leverages
- analyzes

Rules:

GENERAL EXTRACTION:
- Only extract relations that are EXPLICITLY stated in the abstract text.
- Do not use outside knowledge or infer unstated relationships.
- If a relation is uncertain, speculative, or only implied, return nothing.
- Extract at most 5 quadruples. If no valid relation exists, return [].

FOR SURVEY / REVIEW PAPERS:
- Survey papers describe established practices in a field.
- Extract field-level relations when they connect a technical method/technique with a specific task/problem.
- Acceptable patterns:
  * "NLP techniques are used for suicide risk detection"
  * "Deep learning models have been applied to clinical text analysis"
  * "Transformer-based methods achieve state-of-the-art on NER"
- Do NOT extract vague domain-to-domain claims like "NLP addresses healthcare".
- Use relations: applies_to, uses, leverages, addresses, is_evaluated_on, is_based_on, achieves.

ENTITY CONSTRAINTS:
- Subject and object must be scientific concepts, including:
  * model, algorithm, method, technique, framework, system
  * dataset, benchmark, corpus
  * task, application problem, use case
  * metric, measurable finding, scientific phenomenon
  * specific named entity (e.g., "BERT", "UMLS", "MIMIC-III")
- Prefer canonical entity names when available.
  Example: Use "BERT" instead of "BERT model", use "Transformer" instead of "Transformer architecture"
- Do not use vague entities:
  "this paper", "the method", "the approach", "the results",
  "research field", "application area", "multiple layers", or full sentences.
- For tasks, use standard names:
  "named entity recognition", "sentiment analysis", "question answering",
  "clinical information extraction", "suicide risk detection"
- Do not extract broad domain-only relations like "NLP addresses medicine".
- Prefer concrete technical relationships:
  method → task, model → dataset, technique → problem, system → metric.

RELATION CONSTRAINTS:
- relation must be exactly one of the allowed relation labels.
- Choose a relation only when the abstract clearly supports it.
- Avoid forcing relations when no suitable label exists.

ENTITY VALIDATION:
- Reject entities that describe:
  difficulty, quality, importance, outcome magnitude, or abstract concepts.

Reject examples:
"laborious analysis"
"better performance"
"high quality inference"
"depth of understanding"
"scientific issues"
"research development"

- The subject should usually be an active technical method, model,
algorithm, system, dataset, benchmark, or technique.

- Data sources alone cannot perform actions.
Reject:
"social media data detects suicide risk"

Prefer:
"NLP model detects suicide risk"

RELATION VALIDATION:
- For detects, predicts, classifies, extracts, generates:
  the subject must be a computational method, model, algorithm, or technique.
  Methods and frameworks are acceptable as subjects.

- For increases, reduces, improves_upon, outperforms:
  only use when the abstract reports a direct measured comparison.

- For applies_to, uses, leverages, analyzes:
  use for established practices described in surveys or reviews
  when connecting methods/techniques to tasks/problems.

Do not extract from speculative language:
"potential"
"promise"
"can help"
"may"
"could"
"likely"
"tends to"
