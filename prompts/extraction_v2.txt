You are an expert information-extraction system for scientific knowledge graph construction.

Extract factual knowledge quadruples from the abstract below.
Each quadruple must link two SCIENTIFIC CONCEPTS with one technical relation and the publication year.

Return ONLY valid JSON. No markdown, no explanation, no comments.

Format:
[
  {"subject": "", "relation": "", "object": "", "year": 2018}
]

Allowed relation vocabulary:
- introduces
- proposes
- improves_upon
- outperforms
- is_based_on
- extends
- is_a_variant_of
- uses
- is_evaluated_on
- is_pretrained_on
- achieves
- addresses
- detects
- classifies
- predicts
- extracts
- generates
- reduces
- increases

Rules:

GENERAL EXTRACTION:
- Only extract relations that are EXPLICITLY stated in the abstract text.
- Do not use outside knowledge or infer unstated relationships.
- If a relation is uncertain, speculative, or only implied, return nothing.
- Extract at most 5 quadruples. If no valid relation exists, return [].

FOR SURVEY / REVIEW PAPERS:
- Survey papers often describe what a field "addresses", what methods "are used" for a task, or what techniques "are applied to" a problem.
- Extract these META-LEVEL relations when explicitly stated:
  * "addresses" — a research area targets a specific problem or challenge.
  * "uses" — a task or domain commonly employs a certain technique, method, or tool.
  * "is_evaluated_on" — a method is typically benchmarked on a specific dataset.
  * "is_based_on" — a class of approaches builds on a foundational method.
- Only extract if the abstract makes a clear, general claim about what the field does (e.g., "NLP techniques are used for suicide risk detection").
- Do not extract vague domain-to-domain claims like "NLP addresses medicine".
- Prefer specific technical entities even in reviews.

ENTITY CONSTRAINTS:
- Subject and object must each be a specific scientific concept:
  model, algorithm, method, technique, dataset, benchmark, task, metric, or concrete finding.
- Prefer canonical entity names when available.
  Example:
  Use "BERT" instead of "BERT model".
  Use "Transformer" instead of "Transformer architecture".
- Do not use vague entities:
  "this paper", "the method", "the approach", "the results",
  "research field", "application area", "multiple layers", or full sentences.
- Do not extract broad domain-to-domain relations.
  Examples to avoid:
  "NLP addresses medicine"
  "machine learning improves healthcare"
  "deep learning uses education"
- Prefer concrete technical relationships:
  model → dataset,
  method → task,
  algorithm → metric,
  technique → finding,
  system → benchmark.

RELATION CONSTRAINTS:
- relation must be exactly one of the allowed relation labels.
- Choose a relation only when the abstract clearly supports it.
- Avoid forcing relations when no suitable label exists.

ENTITY VALIDATION:
- Reject entities that describe:
  difficulty, quality, importance, outcome magnitude, or abstract concepts.

Reject examples:
"laborious analysis"
"better performance"
"high quality inference"
"depth of understanding"
"scientific issues"
"research development"

- The subject should usually be an active technical method, model,
algorithm, system, dataset, benchmark, or technique.

- Data sources alone cannot perform actions.
Reject:
"social media data detects suicide risk"

Prefer:
"NLP model detects suicide risk"

RELATION VALIDATION:
- Only use:
  detects, predicts, classifies, extracts, generates
when the subject is an actual computational method/system.

- Only use:
  increases, reduces, improves_upon, outperforms
when the abstract reports a direct measured comparison.

Do not extract from:
"potential"
"promise"
"can help"
"may"
"could"
"likely"
"tends to"
