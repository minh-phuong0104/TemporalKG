You are an expert information-extraction system for scientific knowledge graph construction.

Extract factual knowledge quadruples from the abstract below.
Each quadruple must link two SCIENTIFIC CONCEPTS with one technical relation and the publication year.

Return ONLY valid JSON. No markdown, no explanation, no comments.

Format:
[
  {{"subject": "", "relation": "", "object": "", "year": 2018}}
]

Allowed relation vocabulary:
- introduces
- proposes
- improves_upon
- outperforms
- is_based_on
- extends
- is_a_variant_of
- uses
- is_evaluated_on
- is_pretrained_on
- achieves
- addresses
- detects
- classifies
- predicts
- extracts
- generates
- reduces
- increases
- applies_to
- supports
- integrates
- leverages
- analyzes

Rules:

EXTRACTION PRIORITY:
- Prefer extracting useful scientific relations over returning empty output.
- If a sentence explicitly states that a method/technique is used for a task/problem, extract the relation.
- Review papers describe established practices. Extract these as factual relations.
- Do not avoid extraction simply because the paper is a review or survey.

GENERAL EXTRACTION:
- Only extract relations that are EXPLICITLY stated in the abstract text.
- Do not use outside knowledge or infer unstated relationships.
- If a relation is uncertain, speculative, or only implied, return nothing.
- Extract at most 5 quadruples. If no valid relation exists, return [].

ENTITY TYPES:
Subject and object can be:
- model, algorithm, method, technique, framework, system
- dataset, benchmark, corpus
- task, scientific problem, application area
- metric, measurable finding, phenomenon
- technical field when referring to a method family (e.g., "Deep Learning", "NLP", "Machine Learning")

Avoid only truly generic concepts without technical meaning like "research", "science", "technology".

ENTITY CONSTRAINTS:
- Prefer canonical entity names when available.
  Example: Use "BERT" instead of "BERT model", use "Transformer" instead of "Transformer architecture"
- For tasks, use standard names:
  "named entity recognition", "sentiment analysis", "question answering",
  "clinical information extraction", "suicide risk detection"
- Do not use vague entities:
  "this paper", "the method", "the approach", "the results",
  "multiple layers", or full sentences.

VALID ENTITY EXAMPLES:
"Deep Learning" (as a method family)
"Natural Language Processing" (as a technique field)
"sentiment analysis" (as a task)
"suicide risk" (as a detection target)
"clinical text" (as a data type)
"MIMIC-III" (as a dataset)
"BERT" (as a model)

RELATION CONSTRAINTS:
- relation must be exactly one of the allowed relation labels.
- Choose a relation only when the abstract clearly supports it.
- Avoid forcing relations when no suitable label exists.

VALID RELATION PATTERNS:
Accept these patterns when explicitly stated:
- Method family → task: "Deep Learning applies_to named entity recognition"
- Technique → problem: "NLP analyzes clinical text"
- Method → detection target: "Machine Learning detects suicide risk"
- Model → dataset: "BERT is_evaluated_on GLUE benchmark"
- Method → application: "NLP techniques are used for screening"

ENTITY VALIDATION:
- Reject entities that describe abstract qualities or magnitudes:
  "laborious analysis", "better performance", "high quality",
  "depth of understanding", "scientific issues", "research development"

- Data sources alone cannot perform actions.
  Reject: "social media data detects suicide risk"
  Accept: "NLP analyzes social media data"

RELATION VALIDATION:
- For detects, predicts, classifies, extracts, generates, analyzes:
  the subject must be a computational method, technique, model, algorithm, or method family.
  Technical fields like "NLP", "Deep Learning", "Machine Learning" are acceptable subjects
  when they represent a family of methods.

- For increases, reduces, improves_upon, outperforms:
  only use when the abstract reports a direct measured comparison.

- For applies_to, uses, leverages, integrates:
  use for established practices, especially in survey/review papers.

Do not extract from speculative language:
"potential", "promise", "can help", "may", "could", "likely", "tends to"
